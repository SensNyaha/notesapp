Проверка после вашего обновления:

1. На iPhone открыть PWA с иконки «Домой», обновить оболочку, войти постоянным аккаунтом и открыть «Уведомления».
2. Нажать «Включить уведомления», разрешить системный запрос. Должны появиться «Разрешено» и «Активна». При отказе изменить разрешение в настройках iOS и нажать «Проверить снова».
3. Нажать «Отправить тест через 10 секунд», свернуть PWA или заблокировать телефон. Ожидается нейтральное уведомление Tasks. Нажатие возвращает в приложение. Принятие сообщения push-службой не подтверждает его показ на телефоне.
4. Отключить уведомления: новый тест недоступен, ожидающее задание отменено. Включить снова, запланировать тест и выйти либо выбрать «Войти снова / другой аккаунт»: прежняя подписка и ожидающий тест отключаются; новый аккаунт включает push отдельно. Переключение аккаунта завершает серверный сеанс, сохраняя локальные профили/хранилища. Уже отправленный push отозвать невозможно.
5. Проверить, что после перезапуска сервера остаются подписка и ключ VAPID. Тест, который ещё актуален, отправляется; просроченный отменяется. После нажатия «Отправить тест» можно повторять проверку не чаще раза в 30 секунд. Срок актуальности — одна минута, максимум три попытки при 429/5xx. При неопределённом сетевом результате автоматический повтор не выполняется.
6. В «Диагностике» выполнить «Проверить шифрование» на iPhone и записать модель, iOS и показанные длительности для окончательного выбора стоимости KDF. Пользователь подтвердил установленный PWA и iOS 26.6.1; реальный push ещё требует этой проверки.

Поддержаны стандартные службы Safari (`web.push.apple.com`), Chrome/Edge (`fcm.googleapis.com`) и Firefox (`updates.push.services.mozilla.com`). Произвольные адреса и перенаправления для отправки не используются. Сервер хранит endpoint и ключи транспортного шифрования подписки, случайный ID устройства, привязку к аккаунту/сеансу и состояние теста. Название устройства, хранилища и заметки в push не передаются. Тестовые записи удаляются через семь дней, подписки — при отключении/отзыве сеанса или ответе службы 404/410.

## Проверка хранилищ и заметок

1. Войти постоянным аккаунтом; создать два хранилища с разными фразами от 6 любых символов. Создать текстовую заметку, дождаться «Сохранено на устройстве», нажать «Готово» и синхронизировать.
2. Перезагрузить страницу: доступ на этом устройстве сохраняется. Нажать «Закрыть хранилище»: его ключ удаляется только здесь. Неверная фраза не создаёт пустое хранилище; правильная открывает прежние заметки. Второе хранилище остаётся открытым.
3. После загрузки данных отключить сеть, перезапустить приложение, выбрать локальный аккаунт и открыть хранилище по фразе. Изменить заметку, дождаться локального сохранения. Вернуть сеть и проверить синхронизацию. Для нового устройства сначала нужен вход и загрузка с сервера.
4. В другом браузерном профиле войти тем же аккаунтом и открыть хранилище своей фразой. Изменить одну заметку независимо на двух устройствах, затем синхронизировать: обе версии должны оставаться в списке с соответствующей подписью.
5. На первом устройстве выбрать «Забыл фразу · перенести», задать новое название/фразу и подтвердить удаление источника. После завершения старое хранилище удаляется на сервере. На втором устройстве с неотправленными изменениями появится стеш: перенести в открытое хранилище, оставить на потом или удалить с подтверждением. Закрытый источник потребует прежнюю фразу для чтения его локальных изменений.
6. Проверить выход с неперенесённым стешем: отмена сохраняет данные; подтверждение удаляет локальные данные и ключи. «Войти снова / другой аккаунт» позволяет сменить серверный вход с сохранением локальных профилей; это отдельное действие от выхода с очисткой.

Фраза не сохраняется приложением и не отправляется на сервер. Сохраняются неэкспортируемые CryptoKey в IndexedDB; это не аппаратный сейф. Очистка данных сайта удалит локальные ключи и стеш. Без фразы и устройства с сохранённым доступом восстановить содержимое нельзя; recovery-кодов и административной расшифровки нет.

Редактор показывает завершённое локальное сохранение только после транзакции IndexedDB. Последний ввод до фиксации может потеряться при принудительном завершении браузера. При ошибке сохранения не закрывайте страницу и используйте повтор. Временные границы MVP: 1 МиБ открытого JSON записи, 100 активных хранилищ, 10000 неизменяемых версий или 64 МиБ шифротекста на хранилище. При достижении лимита локальная очередь не удаляется; актуальные заметки можно перенести в новое хранилище.

Обычное закрытие не меняет другие устройства. «Закрыть на всех устройствах» записано на следующий этап по решению пользователя. Текущие автоматические тесты используют fake-indexeddb и Fastify inject; проверка Safari/реального браузерного хранилища отдельно необходима. Подробности: `docs/ARCHITECTURE.md`, `docs/CRYPTO_FORMAT.md`, `docs/VAULT_TRANSFER.md`.

## Пользователи и пароли

Кнопка «Пользователи» доступна администратору в диагностике: список логинов, ролей, дат создания, состояний пароля, создание обычного пользователя и выдача нового временного пароля. Дополнительные администраторы, смена логина/роли, блокировка и удаление отложены.

Пароль вводится вручную с повтором либо генерируется из 16 случайных символов. В результате можно скопировать пароль; после закрытия посмотреть его повторно нельзя. Передача пользователю выполняется администратором самостоятельно, без встроенной отправки сообщений. Буфер обмена может сохраняться в истории ОС; приложение не очищает его автоматически.

Временный пароль действует **48 часов от выдачи**, без продления при входе. До истечения срока нужно войти и сменить пароль. До смены доступны операции авторизации, собственная обязательная смена и выход. Управление аккаунтами заблокировано сервером, в том числе для восстанавливаемого admin. Публичный health и оболочка сохраняют своё назначение.

Обязательная смена отзывает все прежние сессии и создаёт новую текущую. Обычная смена доступна каждому: текущий пароль, новый, повтор и включённый по умолчанию флажок «Выйти на других устройствах». Снятый флажок сохраняет другие сессии. Новый пароль отличается от текущего. Сброс администратором всегда немедленно отзывает все сеансы.

Пароли не сохраняются открытым текстом в БД, логах и кешах. Поля находятся в памяти формы; браузер может отдельно предложить сохранение своим менеджером паролей. Перезагрузка очищает поля. Потеря ответа не вызывает автоматический повтор изменения: проверьте список/состояние, а после смены собственного пароля при потере сессии войдите с новым паролем. Повтор создания не создаёт дубль; повтор сброса со старой версией аккаунта отклоняется.

## Команды администратора

Нужен интерактивный терминал (без -T). Пароли не принимаются аргументом, ENV или pipe. Ручной ввод скрыт и требует повтора; Ctrl+C отменяет ввод. Сброс требует подтверждения вводом логина.

```powershell
docker compose exec app npm run user:create -- seconduser
docker compose exec app npm run user:create -- anotheruser --generate
docker compose exec app npm run user:reset -- seconduser --generate
docker compose exec app npm run admin:recover -- adminlogin --generate
```

Замените логины своими. user:reset работает только с обычным пользователем, admin:recover — только с существующим admin. Оба выдают временный пароль на 48 часов. CLI использует общий с UI сервис, не создаёт первого администратора, не мигрирует и не создаёт отсутствующую БД. CLI запускает оператор с доступом к серверу; HTTP требует сессию admin. Пароль выводится один раз после успеха и остаётся в истории вывода терминала, не в истории аргументов команд.

## Пользовательская проверка этапа 04

1. Войти прежним администратором без обязательной смены. При старой оболочке перезагрузить с сетью и нажать «Обновить приложение».
2. Создать тестового пользователя вручную: проверить неверный/занятый логин, правила пароля и несовпадающий повтор. Создать второго через генерацию; проверить копирование и закрытие результата.
3. В другом профиле браузера войти временным паролем. Обязательная смена показывает логин и срок; пропустить нельзя, перезагрузка возвращает к ней. Проверить неверный текущий, совпадающий с ним новый и несовпадающий повтор.
4. Сменить пароль и проверить вход новым: роль «Пользователь», нет управления пользователями. /api/auth/users возвращает запрет. Старый пароль больше не подходит.
5. В двух профилях войти одним тестовым аккаунтом. Обычная смена без флажка сохраняет второй сеанс; с флажком после следующей проверки/запроса потребуется вход. Сброс администратором прекращает все старые сессии.
6. Выдать новый временный пароль с подтверждением, повторно проверить обязательную смену. Ровно 48 часов покрыты тестом с управляемыми часами; менять системные часы сервера не нужно.
7. Проверить CLI создания/сброса на тестовом пользователе. Восстановление admin проверять на отдельной установке либо осознанно, имея доступ к серверу: оно завершит все его сеансы.
8. iPhone: прокрутка с клавиатурой, доступные кнопки, отсутствие горизонтального скролла, портрет/альбом и safe areas. Компьютер: Tab/Shift+Tab/Enter, видимый фокус, показ/скрытие паролей, назад/отмена.
9. Отключить сеть во время формы: понятная ошибка без ложного успеха. После восстановления проверить результат до повтора; перезагрузка очищает секретные поля. В Console нет JS/CSP-ошибок, в Local Storage/IndexedDB нет паролей/токенов, API не кешируется SW.
10. Перезапустить контейнер: аккаунты/пароли/сессии и installationId сохраняются. Через 16 минут вернуться во вкладку или выполнить действие: access продлевается через refresh.

Этап принят пользователем; перечень проверенных устройств не уточнялся. Браузерный инструмент агента вернул пустой список браузеров, поэтому собственную проверку Safari/PWA агент не заявляет. По решению пользователя агент пересобирает и обновляет существующий Compose-сервис; дополнительные тестовые контейнеры не создаёт.

## Первый администратор и новая установка

При пустой установке обе валидные переменные BOOTSTRAP_ADMIN_LOGIN и BOOTSTRAP_ADMIN_PASSWORD создают admin до открытия HTTP-порта. Обе отсутствуют/пусты — первый вход показывает предупреждение о роли и повтор пароля. Частичная/невалидная пара блокирует запуск без вывода значений. После настройки ENV игнорируется и не меняет пароль, даже после восстановления admin командой.

Если .env ещё нет, скопируйте .env.example и заполните локально. Он исключён из Git/Docker context. Пароль со знаком $ в .env заключайте в одинарные кавычки. После создания можно убрать bootstrap-данные и пересоздать контейнер. Без ENV первый посетитель ненастроенного приложения может стать admin — согласованный fallback. Для опубликованной установки задайте ENV заранее.

Новой установке backup старой БД не нужен: ENV, verify/build, compose up. Логин: 3–32 ASCII-символа, первая латинская буква, далее латиница/цифры/точка/дефис/подчёркивание, регистр не различается. Пароль: 6–128 Unicode-символов, цифра 0–9, верхний и нижний регистр, без обрезки пробелов/нормализации. Argon2id v19, 64 MiB, t=3, p=1, соль16, хеш32.

## Сессии и адрес приложения

Access — 15 минут; refresh — 30 дней от обновления, абсолютный предел 90 дней от входа. Для временного пароля дополнительно 48 часов от выдачи. Проверка на запуске, возврате во вкладку, восстановлении сети и перед операциями аккаунта. Токены opaque, HttpOnly-cookie; в SQLite только SHA-256-хеши.

Ротация refresh транзакционная. Повтор в течение 10 секунд возвращает ту же пару; поздний повтор старого токена отзывает семейство. Короткий повтор также доступен обладателю старого токена и CSRF-данных; бессрочного принятия нет. Потеря ответа вне окна может требовать входа. Web Locks координирует обновления вкладок при поддержке браузером.

Cookie SameSite=Strict, Path=/, без Domain; HTTPS добавляет Secure и __Host-. CSRF: exact Origin, JSON и заголовок с токеном из same-origin endpoint. Compose: APP_ORIGIN=http://localhost:3100, AUTH_COOKIE_MODE=localhost. Для HTTPS: точный APP_ORIGIN=https://tasks.DOMAIN, AUTH_COOKIE_MODE=secure. Nginx/HTTPS — отдельный этап; localhost компьютера не является адресом телефона.

Лимиты на процесс: 10 входов/15 минут на IP и логин, 120 изменяющих auth-запросов/минуту/IP, 20 операций аккаунтов с хешированием/минуту/IP, 10 попыток смены пароля/15 минут на аккаунт, максимум 2 параллельных Argon2 в HTTP. Счётчики сбрасываются при рестарте; CLI не объединяет лимиты с HTTP-процессом. За proxy IP пока является адресом соединения; trustProxy согласуется при HTTPS-развёртывании.

## Резервное копирование и откат этапа 04

Снимки содержат хеши паролей и сессий; ограничьте доступ. backups/ исключён из Git/Docker context. Текущий снимок схемы 3:

```powershell
docker compose exec app node server/cli/backup.mjs /data/tasks.sqlite /data/stage04-current.sqlite
```

Для отката код берётся из Git и пересобирается в том же Compose-сервисе. Сначала сохраните текущие изменения в Git, запишите текущий коммит для возврата и убедитесь, что рабочее дерево чистое. Нужен снимок схемы 2, сделанный до перехода на 0.4.0: Git не восстанавливает БД. Без него откат к 0.3.0 с сохранением данных не предусмотрен.

Подготовить текущий снимок и восстановить схему 2 в **новый каталог**, пока текущий контейнер ещё работает:

```powershell
docker compose exec app node server/cli/backup.mjs /data/tasks.sqlite /data/stage04-before-rollback.sqlite
docker compose exec app node server/cli/restore.mjs /data/before-stage04.sqlite /data/restored-before-stage04
@'
services:
  app:
    image: tasks:0.3.0
    environment:
      DATA_DIR: /data/restored-before-stage04
'@ | Set-Content -Encoding UTF8 backups/rollback-stage04.yaml
docker compose stop app
git switch --detach c051f9c
docker compose -f compose.yaml -f compose.ca.yaml build app
docker compose -f compose.yaml -f backups/rollback-stage04.yaml up -d --no-build --force-recreate app
curl.exe -fsS http://localhost:3100/api/health
```

Ожидаются 0.3.0 и прежний installationId из снимка. Схема 2 содержит состояние аккаунтов/паролей/сеансов на момент backup: поздние изменения отсутствуют, прежние пароли/сеансы могут снова действовать. Исходная схема 3 и её копия сохраняются. Старый образ не открывает схему 3. Restore откажет при существующем каталоге; выберите новое имя и измените DATA_DIR override согласованно. Не удаляйте WAL, данные сайта или Docker volume как штатный откат.

Не перезаписывайте ранее сохранённый backups/rollback-stage04.yaml; при необходимости выберите другое имя. После отката используйте сохранённый rollback-override. При возвращении к новому коммиту обычный compose снова выберет 0.4.0 и исходный /data; перед обновлением определите рабочую копию БД. Инструкции этапа 03 доступны в истории Git.
