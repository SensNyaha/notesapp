# Tasks — этап 03, версия 0.3.0

PWA для заметок, напоминаний и планирования. Сейчас реализованы диагностическая оболочка и первый администратор: создание из ENV или через первый вход, вход/выход, серверные access/refresh-сессии. Клиент — Preact/TypeScript/Vite; сервер — Fastify/Node 24; SQLite WAL, схема 2.

Создание остальных пользователей через UI и команду, временные пароли и их обязательная смена — следующий этап. Заметки, хранилище и push ещё не реализованы. Вопросы разблокировки хранилища отложены до соответствующего этапа по решению пользователя. Приёмка этапа 03 пользователем ожидается.

## Первый администратор

При первоначальном запуске, если аккаунтов ещё нет:

- Обе переменные `BOOTSTRAP_ADMIN_LOGIN` и `BOOTSTRAP_ADMIN_PASSWORD` заполнены корректно — администратор создаётся до открытия HTTP-порта.
- Обе отсутствуют или пусты — после попытки входа появляется уведомление о создании администратора, повтор пароля, подтверждение и отмена. До подтверждения аккаунт не создаётся.
- Заполнена только одна переменная или данные не проходят правила — запуск завершается понятной ошибкой, значения секретов не выводятся.
- Если первоначальная настройка уже завершена, ENV не создаёт аккаунты и не меняет пароль. Настройка не открывается заново даже после удаления всех пользователей сторонними средствами.

Для настройки скопируйте `.env.example` в `.env`, если `.env` ещё нет, и заполните его локально. Файл `.env` исключён из Git и Docker build context. Пароли не присылайте агенту. В `.env` значения пароля со знаком `$` заключайте в одинарные кавычки, чтобы Compose не подставлял переменные. После успешного создания рекомендуется убрать bootstrap-логин/пароль из `.env` и пересоздать контейнер: существующий пароль в БД сохранится. Оператор Docker имеет доступ к окружению контейнера.

Логин: 3–32 символа, первая — латинская буква, далее латиница, цифры, `.`, `_`, `-`; регистр не различается. Пароль: 6–128 Unicode-символов, минимум одна цифра 0–9, заглавная и строчная буквы (латиница или кириллица). Пробелы не обрезаются, регистр не меняется. Для хранения используется Argon2id: 64 MiB, 3 прохода, параллелизм 1, соль 16 байт, хеш 32 байта.

При отсутствии ENV ещё не настроенное приложение доступно для создания первого администратора тому, кто откроет его первым. Это предусмотренный fallback; для опубликованного приложения задайте ENV до запуска.

## Обновление существующего этапа 02 через Docker

Все команды — из корня проекта в PowerShell. Выполняйте по одной и останавливайтесь при ошибке. Команды с CA используют уже настроенный `certs/npm-ca.pem`. Если дополнительный CA не нужен, уберите `--secret ...` и `-f compose.ca.yaml`. Не отключайте TLS-проверку.

Сначала сохранить старый образ, собрать и проверить новый, **не запуская новый сервер на старой БД**:

```powershell
docker image tag tasks:0.1.1 tasks:before-stage03
docker build --secret id=npm_ca,src=certs/npm-ca.pem --target verify -t tasks:stage03-verify .
docker compose -f compose.yaml -f compose.ca.yaml build app
curl.exe -fsS http://localhost:3100/api/health
```

Не перезаписывайте тег `tasks:before-stage03` после обновления. Запишите installationId. Target verify выполняет typecheck, build и все тесты в Node 24; обычная сборка runtime тесты отдельно не запускает.

Создать согласованный снимок схемы 1 новым инструментом, который **не запускает миграции**, и выгрузить его на хост:

```powershell
docker compose run --rm --no-deps app node server/cli/backup.mjs /data/tasks.sqlite /data/before-stage03.sqlite
New-Item -ItemType Directory -Force -Path .\backups | Out-Null
$tasksContainer = docker compose ps -q app
docker cp "${tasksContainer}:/data/before-stage03.sqlite" .\backups\before-stage03.sqlite
```

Ожидается `schemaVersion: 1`. Инструмент использует SQLite backup API и integrity_check; не копирует только основной файл при активном WAL. Если файл назначения уже существует, команда откажет — не удаляйте прежний снимок, выберите новое имя и используйте его далее. Файл на хосте также не должен заменять нужную прежнюю копию.

Подготовьте `.env` по разделу выше, затем обновите:

```powershell
docker compose -f compose.yaml -f compose.ca.yaml up -d --no-build
docker compose ps
curl.exe -fsS http://localhost:3100/api/health
docker compose logs --tail 100 app
```

Ожидается healthy, версия 0.3.0, прежний installationId, увеличенный bootCount. Миграция в схему 2 выполняется транзакционно. После перезапуска аккаунт и сессии сохраняются:

```powershell
docker compose restart app
curl.exe -fsS http://localhost:3100/api/health
```

Для полностью новой установки снимок схемы 1 не нужен: подготовить `.env`, выполнить сборку/verify и `docker compose -f compose.yaml -f compose.ca.yaml up -d --no-build`.

## Пользовательская проверка

1. Открыть `http://localhost:3100`. Если осталась старая оболочка, перезагрузить с сетью, дождаться уведомления и нажать «Обновить приложение». При необходимости DevTools → Application → Service Workers → Update, без Bypass for network и Update on reload.
2. Без bootstrap-ENV: ввести логин и пароль, нажать «Войти». Должно появиться уведомление о первом администраторе. Проверить несовпадающий повтор и отмену; затем подтвердить правильный повтор. В режиме с ENV сразу войти созданными данными, без повторного создания.
3. После входа видны логин, роль «Администратор», «Выйти» и прежняя диагностика. Новых заметок и управления пользователями пока нет. Проверить выход, неверный пароль и повторный вход. Ссылка восстановления показывает справку о том, что функция пока не реализована.
4. Проверить перезагрузку и перезапуск контейнера: вход сохраняется. Через 16 минут вернуться во вкладку или перезагрузить страницу: доступ должен продлиться без пароля. В Network — успешный `/api/auth/refresh`, затем `/api/auth/session`.
5. Открыть вторую вкладку того же origin, повторить возвращение после истечения access. Обе вкладки должны остаться работоспособными. Другое устройство/браузер имеет отдельную сессию; выход отзывает текущую серверную сессию.
6. Для проверки автоматического создания из ENV и fallback используйте **разные пустые тестовые БД/установки**. Не удаляйте рабочую БД ради повторного первого входа. Изменение ENV при существующем аккаунте не должно менять пароль.
7. На ширинах 390 и 1280 CSS px проверить поля, кнопки, перенос длинного логина, Tab/Enter, фокус и увеличение 200%. На iPhone отдельно проверить клавиатуру, safe areas и поворот. Первоначальная настройка и вход без сети не работают; кешируется только оболочка. Сообщение о сети не должно выдавать успешную авторизацию.
8. В Console не должно быть ошибок JS/CSP. Токены не должны появляться в Local Storage или IndexedDB; cookie токенов HttpOnly. В режиме HTTPS дополнительно Secure. Ответы auth имеют no-store и не кешируются Service Worker.

Браузер и реальный iPhone в сессии агента недоступны. Эти пункты требуют пользовательской приёмки; модельный SW-тест не заменяет проверку браузера. Основной контейнер агент не обновляет автоматически.

## Сессии и адрес приложения

Access действует 15 минут, refresh — 30 дней с последнего обновления; абсолютный предел сессии — 90 дней от входа. Автоматическое продление работает при проверке сессии на запуске, возвращении во вкладку и восстановлении сети, без зависимости от фонового таймера iOS. После выхода, отзыва, очистки cookie или истечения refresh нужен повторный вход.

Оба токена — случайные opaque-значения в HttpOnly-cookie; в SQLite — хеши. Refresh ротируется транзакционно. Повтор того же запроса в течение 10 секунд возвращает ту же пару токенов для восстановления потерянного ответа/конкурирующих вкладок. После этого повтор старого токена отзывает семейство сессии. Такой короткий повтор также доступен тому, кто завладел старым токеном и CSRF-данными в этом окне; бессрочного принятия старых токенов нет. Если ответ потерян и клиент вернулся только после окна повтора, может потребоваться новый вход. В браузерах с Web Locks обновления вкладок дополнительно координируются.

Cookie: SameSite=Strict, Path=/, без Domain; в secure-режиме имена имеют префикс `__Host-`. CSRF: сравнение случайного значения из HttpOnly-cookie с заголовком X-CSRF-Token, полученным через same-origin endpoint, плюс строгая проверка Origin; запросы изменения состояния — JSON. SameSite не является единственной CSRF-защитой.

Compose по умолчанию настроен только на `APP_ORIGIN=http://localhost:3100`, `AUTH_COOKIE_MODE=localhost`. Для `http://127.0.0.1:3100` задайте этот точный origin и используйте именно его. Для будущего HTTPS-домена потребуются `APP_ORIGIN=https://tasks.DOMAIN` и `AUTH_COOKIE_MODE=secure`; localhost-режим для внешнего домена отвергается. Настройка Nginx/HTTPS не входит в текущий этап. Standalone/iPhone проверяются на доступном HTTPS-origin; localhost компьютера не является адресом телефона.

Лимиты: 10 попыток входа/создания за 15 минут на IP и логин, 120 изменяющих auth-запросов в минуту на IP, максимум 2 одновременных Argon2-вычисления на процесс. Счётчики ограничены по памяти и сбрасываются при перезапуске процесса. За reverse proxy сейчас используется адрес соединения без trustProxy, поэтому лимит по IP может быть общим; доверенные proxy и адреса клиентов согласуются при HTTPS-развёртывании.

## Резервное копирование и откат

Снимки содержат хеши паролей и служебные данные сессий: ограничьте доступ и не публикуйте их. Каталог `backups/` исключён из Git и Docker build context. Новый снимок схемы 2 создаётся командой:

```powershell
docker compose exec app node server/cli/backup.mjs /data/tasks.sqlite /data/stage03-current.sqlite
```

Для отката после проверки сначала сохранить текущую БД, затем остановить приложение. Восстановление выполняется **в новый каталог**, старые БД/WAL остаются на месте:

```powershell
docker compose exec app node server/cli/backup.mjs /data/tasks.sqlite /data/stage03-before-rollback.sqlite
docker compose stop app
docker compose run --rm --no-deps app node server/cli/restore.mjs /data/before-stage03.sqlite /data/restored-before-stage03
docker compose -f compose.yaml -f compose.rollback-stage03.yaml up -d --no-build --force-recreate
curl.exe -fsS http://localhost:3100/api/health
```

Ожидается версия 0.1.1, прежний ID из снимка, схема 1 в новом каталоге. `restore.mjs` отказывает, если каталог уже существует; при повторной попытке используйте новое имя и согласованно измените DATA_DIR в override. Администратор, созданный после снимка, отсутствует в старой версии; исходная БД схемы 2 и её отдельный снимок сохранены. Старый образ намеренно не открывает схему 2. Не применяйте `down -v`, очистку данных сайта или удаление WAL как штатный откат.

После отката используйте rollback-override для управления старой версией. Обычный compose без него снова выбирает 0.3.0 и исходный `/data`. Перед следующим обновлением явно определите, какая копия БД является рабочей. Для проверки восстановления до настоящего отката используйте отдельный тестовый контейнер/каталог.

## Без Docker

Нужен Node 24.x. Установленная в окружении агента версия Node 25 годится только для дополнительной проверки; целевые проверки выполнялись на Node 24 в Docker.

```powershell
npm ci
npm run build
npm run check
$env:APP_ORIGIN = 'http://localhost:3100'
$env:AUTH_COOKIE_MODE = 'localhost'
npm start
```

Node не читает `.env` автоматически этим способом. Для чтения локального файла можно использовать `node --env-file=.env server/index.mjs`. По умолчанию DATA_DIR — `./data`; перед первым запуском новой версии на старой БД создайте снимок командой `node server/cli/backup.mjs data/tasks.sqlite backups/before-stage03.sqlite` (родительский каталог должен существовать).

Сборка сначала проверяет типы, затем выполняет Vite и генерацию SW. `npm run check` требует готового dist. `npm audit` — аудит зависимостей. Docker target verify содержит тесты; runtime — только production-зависимости, server, dist и package.json. Для фиксированного `argon2@0.45.1` явно разрешён установочный скрипт в package.json; никаких общих отключений проверки install scripts или TLS нет.
