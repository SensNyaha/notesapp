# Tasks — технический этап 02, версия API 0.1.1

Диагностическая оболочка PWA для заметок и напоминаний. В этапе 02 клиент переведён на TypeScript и Vite. Пользовательская приёмка этапа ожидается; новые продуктовые экраны не добавлены. Надпись «Этап 01» на диагностическом экране и версия API сохранены, поскольку его назначение и контракт не менялись.

Реализовано:

- Preact, интерфейс проверки первого запуска.
- TypeScript: строгая проверка клиента и runtime-проверка контракта health; Vite: хешированные JS/CSS.
- Fastify: API и раздача только заранее известных публичных файлов с одного порта 3100.
- Встроенный `node:sqlite`, SQLite WAL, первая миграция схемы.
- Постоянный идентификатор установки и счётчик запусков сервера.
- PWA manifest, иконки, Service Worker с офлайн-кешем только публичной оболочки.
- Обновление оболочки через кнопку, когда новая версия готова.
- Docker Compose с постоянным томом, healthcheck и ограничением размера логов.

В этом этапе ещё нет аккаунтов, заметок, шифрования записей, IndexedDB, расписания и push. Web Crypto на странице — проверка доступности браузерного API, а не реализованное шифрование. Офлайн работает оболочка приложения, а не заметки. Сервер не принимает пользовательское содержимое.

## Запуск без Docker

Понадобится Node.js 24.x и npm. Docker предпочтительнее: он даёт одинаковую версию Node.js и окружение на разных компьютерах.

```bash
npm ci
npm run build
npm start
```

Открыть http://localhost:3100. По умолчанию сервер слушает 127.0.0.1, SQLite находится в `./data/tasks.sqlite`. После правок клиента повторить `npm run build`; после правок сервера перезапустить `npm start`.

```bash
npm run check
```

Сборка сначала запускает `npm run typecheck`, затем Vite и генерацию Service Worker. Проверку типов можно вызвать отдельно. Тесты запускаются после сборки. Они проверяют API и его клиентский контракт, сохранение идентификатора при повторном открытии SQLite, недоступность исходников через HTTP, пути и HTTP-кеш хешированных ресурсов, исключение API из кеширования, офлайн-оболочку и явную активацию обновления в модели Service Worker. Это не браузерные тесты.

## Проверка и обновление через Docker

Команды ниже выполняются из корня проекта в PowerShell. Для окружения с доверенным CA используется существующий `certs/npm-ca.pem`; TLS-проверки не отключаются. Если дополнительный CA не требуется, уберите `--secret ...` и `-f compose.ca.yaml`.

Перед первой пересборкой сохраните прежний образ и запишите ID установки. Откройте старую страницу в браузере и дождитесь готовности офлайн-оболочки — это позволит проверить обновление существующей установки.

```powershell
docker image tag tasks:0.1.1 tasks:before-stage02
curl.exe -fsS http://localhost:3100/api/health
docker build --secret id=npm_ca,src=certs/npm-ca.pem --target verify -t tasks:stage02-verify .
docker compose -f compose.yaml -f compose.ca.yaml up -d --build
docker compose ps
curl.exe -fsS http://localhost:3100/api/health
```

Остановитесь при ошибке любой команды. Не повторяйте первую команду после обновления: тег отката должен указывать на старый образ. Target `verify` выполняет сборку с проверкой типов и тесты на Node 24; обычная runtime-сборка выполняет typecheck/build, но тестовый target запускается отдельно.

Ожидается: 3 теста проходят, контейнер healthy, прежний installationId, bootCount увеличен. Для повторной проверки постоянных данных:

```powershell
docker compose restart app
curl.exe -fsS http://localhost:3100/api/health
```

После запуска API должен снова отвечать `ok`, с тем же ID и увеличенным счётчиком. Логи доступны через `docker compose logs --tail 100 app`. Обычная остановка — `docker compose stop`; повторный запуск — `docker compose start`.

Визуальная и браузерная приёмка:

1. На старой открытой странице выполните обычную перезагрузку с сетью. Дождитесь «Доступна новая версия оболочки». Если браузер ещё не проверил SW, в DevTools → Application → Service Workers нажмите Update; не включайте Update on reload и Bypass for network.
2. До нажатия кнопки страница должна оставаться работоспособной. Нажмите «Обновить приложение»: страница перезагрузится и уведомление исчезнет. В Network появятся JS/CSS из `/assets/`; старые `/vendor/`, `/app.js` и `/style.css` новой странице не нужны.
3. Убедитесь, что кнопка «Проверить ещё раз» работает и в Console нет ошибок загрузки модулей/CSP. Сравните внешний вид с прежним диагностическим экраном.
4. После готовности оболочки включите Offline в DevTools → Network и перезагрузите страницу. Оболочка открывается, отображается отсутствие связи с сервером. Верните сеть и нажмите «Проверить ещё раз»: состояние снова успешное.
5. Проверьте ширины 390 и 1280 CSS px, масштаб 200%, Tab и заметный фокус; горизонтальной прокрутки страницы быть не должно. На реальном iPhone отдельно проверить safe areas, поворот и standalone на доступном HTTPS-origin. Настройка HTTPS не входит в этот этап.

В проверке Codex: Node 24.21.0 в Docker, сборка и 3 теста прошли; финальный образ запущен на отдельном порту, SQLite сохранила ID после перезапуска, runtime не содержит Vite/TypeScript/@types/node/исходников клиента/сертификата. `npm audit` сообщил 0 уязвимостей. Браузер и реальный iPhone в сессии агента недоступны: пункты выше ожидают проверки пользователем. Основной контейнер на 3100 агент не пересоздавал.

## Откат этапа 02

Для быстрого возврата рабочего приложения после неудачной пользовательской проверки:

```powershell
docker compose stop app
docker image tag tasks:before-stage02 tasks:0.1.1
docker compose up -d --no-build --force-recreate
curl.exe -fsS http://localhost:3100/api/health
```

Том сохраняется; схема SQLite остаётся версии 1. После отката браузеру также нужно получить и активировать прежний Service Worker обычной проверкой обновления. Не очищайте данные сайта как штатный способ отката. До следующей сборки восстановите исходники этапа 01 из сохранённой версии, затрагивая только файлы этапа 02; пользовательские требования и макеты сохраняйте. Не применяйте `git reset --hard`, `git clean` или `docker compose down -v`.

| `docs/DECISIONS.md`        | Принятые решения и следующие этапы                                  |

Клиент использует TypeScript и обычный CSS; Vite собирает Preact из зафиксированной npm-зависимости. Сервер остаётся на ES-модулях JavaScript. Наличие типов не отменяет проверки входных данных во время выполнения. TypeScript, Vite и типы Node устанавливаются только для сборки; в финальный образ копируется дерево зависимостей после `npm prune --omit=dev --ignore-scripts --offline`. Source maps не публикуются. Production по-прежнему обслуживает Fastify на 3100, Vite dev server для эксплуатации не нужен.

Версии npm-зависимостей зафиксированы в `package.json` и `package-lock.json`; используйте `npm ci`. Образ Node.js закреплён на ветке 24 LTS Debian Bookworm, но тег получает исправления. Простая работа с SQLite изолирована в `server/db.mjs`, поэтому возможное изменение API `node:sqlite` не затронет формат БД. Перед хранением реальных данных ещё раз оценим зрелость этого API и зафиксируем точный образ. Для точного отката сохраняйте предыдущий образ перед следующими этапами.
